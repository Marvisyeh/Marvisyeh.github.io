ETL Pipeline with Apache Airflow

自動化中央氣象署 36 小時天氣預報資料的 ETL 管道，從 API 抽取到 PostgreSQL 入庫，並兼顧穩定性與可維護性。

Sep 09, 2020
1 minute read

專案背景：為什麼需要這個管線？

在這個專案中，我的目標是自動化取得中央氣象署的 36 小時天氣預報，提供給內部系統做後續分析與應用。

一開始的痛點是：

  • 手動打 API 抓資料，非常耗時，而且容易忘記或操作失誤
  • API 回傳的 JSON 結構很複雜，不適合直接給分析或報表使用
  • 缺乏一個可排程、可監控、可重跑的標準化流程

因此我設計了一個以 Apache Airflow 為核心 的 ETL Pipeline，自動在固定時間從 CWB API 抽取資料、轉換成結構化格式，最後寫入 PostgreSQL。

架構總覽

這個 Pipeline 可以拆成三個主要階段：

  1. Extract：extract_data_from_api

    • 透過 Python Operator 呼叫中央氣象署 API
    • 將臺北市的 36 小時預報資料儲存成原始 JSON 檔案
    • 實作簡單的錯誤處理與重試機制，避免短暫網路/服務異常導致整個排程失敗

  2. Transform：transform_data_use_pandas

    • 使用 Pandas 解析巢狀 JSON 結構
    • 將欄位整理成適合關聯式資料庫儲存的表格形式
    • 根據需求產出對應的 SQL Insert / Upsert Script

  3. Load：write_to_sqlserever

    • 透過 Postgres Operator 執行上一步產生的 SQL
    • 將資料寫入目標資料表，更新最新的 36 小時預報資訊

Extract：處理外部 API 的不穩定性

在抽取（Extract）階段，我主要解決兩個問題：

  • API 偶爾會 Timeout 或回傳非 200 狀態碼
  • API 格式未必穩定，若欄位結構改變，可能整條 Pipeline 掛掉

我的實作重點包括：

  • 對 API 呼叫加上 重試機制（例如重試 3 次、逐次延長等待時間）
  • 對回傳內容做基本的 Schema 檢查（例如必須包含 records.location 等欄位）
  • 無論成功與否，都在 Airflow Log 中留下足夠資訊，方便之後追蹤

心得：在 Data Pipeline 裡，「如何面對外部系統的不穩定」往往比「寫出一個完美的程式」更重要。

Transform：用 Pandas 整理巢狀 JSON

中央氣象署的 API 回傳結構相對複雜，包含多層巢狀的 location、weatherElement、time 等欄位。
如果直接把整包 JSON 丟進資料庫，後面要查詢或分析會非常痛苦。

在 Transform 階段，我做了幾件事：

  • 將巢狀 JSON 攤平，拆解出「時間區間」、「地點」、「氣象要素（例如溫度、降雨機率）」等欄位
  • 轉成 DataFrame 後，再根據資料模型設計產出需要的欄位
  • 最後把整理好的 DataFrame 轉成 SQL Script，給下一個 Task 使用

這一段的重點不是「Pandas 多厲害」，而是：

  • 把 原始 API 的結構 和 分析/報表需要的結構 明確切開
  • 讓未來如果 API 有變動，只要調整這一層 Transform 邏輯即可

Load：安全地寫入 PostgreSQL

在 Load 階段，我透過 Postgres Operator 執行上一階段產生的 SQL。
實務上比較需要注意的是：

  • 是否會有「重複寫入」的問題（例如同一時間區間資料被寫兩次）
  • 是否需要用 Upsert（ON CONFLICT）來處理同一筆主鍵的更新
  • 寫入失敗時，要怎麼讓 Airflow 清楚標記這次 Run 是失敗的，方便排查

在這個專案中，我的做法是：

  • 以「城市 + 起始時間 + 氣象要素」作為組合鍵
  • 在 SQL 中使用 Upsert 邏輯（若已存在就更新）
  • 保持 Load 階段邏輯相對單純，只專心負責「正確寫入」

結果與影響

雖然這不是一個超大型的生產環境專案，但對我來說是很重要的一次實戰練習。
完成後，我至少達成了以下幾點：

  • ✅ 將原本需要手動打 API、整理資料的流程完全自動化
  • ✅ 無論前一天是否成功，在固定時間都會有最新的 36 小時預報入庫
  • ✅ 抽取、轉換、寫入三個步驟清楚分開，遇到錯誤較容易定位在哪個階段
  • ✅ 若未來要擴充到其他城市或其他氣象要素，只需要在現有框架下調整設定即可

從這個專案學到什麼？

這個專案讓我對「Data Pipeline 實務」有幾個更具體的體會：

  1. 可觀測性（Observability）很重要
    光是有排程不夠，還要能快速知道「哪裡壞掉、為什麼壞掉」。

  2. 要習慣外部 API 會壞、會變
    在 Extract 階段加入重試、校驗、Log，是讓系統變得更穩定的關鍵。

  3. 分層設計可以降低維護成本
    把 Extract / Transform / Load 拆成不同 Task，讓每一層關注點更單純，也比較好重構。
