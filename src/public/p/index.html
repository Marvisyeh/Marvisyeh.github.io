專案背景：服務和資料平台很多，但沒有統一的異常視角

在很多成長中的團隊裡，應用服務和資料平台越建越多：

  • 多個後端服務，各自把 log 打到自己的檔案或 APM
  • 數據平台會再把部分 log / metrics 匯入資料倉儲做離線分析
  • 風控或合規團隊另外有一套報表或查詢系統追交易異常

結果就是：大家都有 log，但沒有一個地方可以「一次看清楚，正在發生哪些異常」。

對資料工程 / 平台工程來說，這帶來幾個典型痛點：

  • 事件分散在不同系統，很難回答：「某個 user 在這 5 分鐘內，跨服務到底發生了什麼事？」
  • 線上告警（Discord / Slack）和離線儲存（S3 / Data Warehouse）之間，沒有共同的事件來源與 schema
  • 想要對「異常」做進一步分析或模型訓練，卻缺少一張「統一的 anomaly_events 表」可以直接查詢與 join

這個專案的出發點，就是從 資料工程的角度，實作一條「把異常事件統一起來」的 streaming pipeline：

  • 即時性：透過 Kafka + rule-based consumer，幾秒內判斷是否為異常，並發出 Discord 告警
  • 可追溯性：所有原始事件先備份到 S3，異常事件整理後寫入 PostgreSQL anomaly_events，方便回放與分析
  • 統一視角：用 FastAPI 暴露統一 API，React Dashboard 以一個畫面整合 logs / metrics / transactions 的異常資訊

從實作上，我刻意把這個系統設計成一個資料工程導向的練習場：

  • Streaming pipeline 設計：Kafka topics 如何切分、Producers / Consumers 邊界怎麼畫
  • 儲存與 schema：S3 + Postgres 的分工，以及 anomaly_events 的欄位設計
  • 服務化與可觀測性：把「異常事件」整理成穩定 API 給前端與其他服務用，而不是只停留在一堆 raw log

所以它不只是「一個可以跑的 demo」，而是刻意把資料工程在「多系統、多平台但缺乏統一 log 視角」時會遇到的幾個關鍵議題（事件建模、流處理、備援、回溯、API 化）包在同一個專案裡。

系統總覽：事件從哪裡來、要被誰用？

我把整個系統拆成五個角色，對應典型資料平台裡的幾個層次：

  1. Producers（事件產生）

    • 三個 Python producers 模擬 logs / metrics / transactions
    • 以 JSON 格式持續將事件寫入 Kafka 對應的 topics

  2. Consumers（處理與分流）

    • BackupS3Consumer：負責長期備援，把原始 JSON 依日期寫入 S3
    • AnalysisConsumer：依事件類型套用規則，判斷異常、發 Discord 告警並寫入 Postgres

  3. Storage 層

    • S3：原始事件的 data lake-ish 儲存，支援之後的 replay / offline 分析
    • PostgreSQL：以 anomaly_events 為中心的結構化查詢介面

  4. API 層（FastAPI）

    • dashboard 模組：提供總覽、timeline、服務彙總等 dashboard 資料
    • events 模組：提供 anomaly events 的查詢、分頁與統計

  5. 觀測與呈現（React Dashboard）

    • 即時顯示異常事件趨勢、分佈與詳細內容
    • 做為 SRE / 資料工程 / 風控團隊的「共同介面」

從資料工程的視角來看，這是一條「從事件生成 → 串流 → 長期儲存 → 異常化簡 → API 化 → 可視化」的端到端管線。

資料流與事件生命週期

一個事件（例如一筆錯誤 log 或高金額交易）在系統裡的生命週期大致如下：

  1. 產生（Produce）

    • Producer 將事件打到對應 Kafka topic：logs、metrics 或 transactions

  2. 備援（Backup to S3）

    • BackupS3Consumer 從這些 topics 消費原始 JSON
    • 依日期與時間寫入 S3：PREFIX/YYYYMMDD/<timestamp>.json
    • 目的：保留原始事件，支援 replay、offline 訓練與稽核需求

  3. 規則偵測（Rule-based Analysis）

    • AnalysisConsumer 依事件類型套用不同規則：
      • Logs：3 分鐘內 ERROR 大量增加、訊息包含 “failed”、單一 user 錯誤暴增
      • Metrics：CPU 長時間 >= 80%、latency > 1000ms，或兩者同時偏高
      • Transactions：單筆金額 > 10000，或 5 分鐘內單一 user 高頻交易
    • 若判定為異常：
      • 觸發 Discord webhook 發送告警
      • 轉成 anomaly_events 結構後寫入 PostgreSQL

  4. 查詢與統計（Query & Aggregation）

    • FastAPI 將 anomaly_events 上的查詢與統計封裝成穩定 API
    • 包含：事件列表、單筆詳細、統計摘要、按時間/服務的分佈等

  5. 可視化與監控（Visualization & Monitoring）

    • React Dashboard 透過 API 取得資料並呈現
    • 以圖表與清單形式給 SRE / 工程師 / 風控同一個「異常視角」

這樣的設計，讓「即時告警」、「離線分析」、「模型訓練」可以共享同一批事件，而不是各自處理各自的 log。

CREATE TABLE anomaly_events (
  id TEXT PRIMARY KEY,
  timestamp TIMESTAMPTZ,
  is_alert BOOLEAN,
  alert_type TEXT,
  alert_level TEXT,
  alert_title TEXT,
  alert_message TEXT,
  user_id TEXT,
  tags JSONB,
  metrics JSONB
);
``+

設計考量：

- `id`：使用文字主鍵（例如 UUID），便於跨服務產生與追蹤  
- `alert_type`：標記事件來源類型（log / metric / transaction）  
- `alert_level`：嚴重程度（info / warning / critical…）  
- `tags`：彈性的 metadata（service、region、host、環境等）  
- `metrics`：事件相關數值（CPU%、latency、交易金額…）  

這張表的角色類似「異常事件的事實表」，  
讓 BI 報表、即時監控、甚至未來的風險模型，都可以有一個穩定可 join 的來源。

## 規則引擎設計：為什麼先用 Rule-based？

在很多實務場景中，團隊一開始就想用 ML 做 anomaly detection，  
但實際落地時，rule-based 常常是**更好的第一步**：

- 各團隊（SRE、風控、產品）對規則的語意容易達成共識  
- 行為可預期、可解釋，對合規/稽核友善  
- 可以先透過規則累積帶標籤的異常事件，未來才有 ML 訓練資料  

在這個專案裡，我刻意將規則寫得「業務語意清楚」：

- log：在 3 分鐘內錯誤數暴增，或特定關鍵字出現  
- metric：CPU 長時間高於某個門檻 + latency 同時偏高  
- transaction：單筆或短時間內的金額/頻率異常  

這些規則都對應到現實世界會關心的問題，  
同時也讓之後要引入統計或 ML 模型時，有一個良好的 baseline 可以比較。

## API 設計：把異常事件服務化

為了讓前端與其他系統不需要直接碰資料庫，我用 FastAPI 設計了一層 API：

- `GET /events`：  
  - 查詢異常事件列表，支援 filter（type、level、user、時間區間）與分頁  
- `GET /events/{event_id}`：  
  - 取得單一事件詳細資訊  
- `GET /events/stats/summary`：  
  - 取得統計摘要（依 type、level 的分佈等）  
- `GET /dashboard/overview`：  
  - Dashboard 總覽指標（近期 alert 數量、分布等）  
- `GET /dashboard/timeline`：  
  - 以時間軸呈現近期告警  
- `GET /dashboard/services`：  
  - 依 service 彙總健康狀況  

API 採模組化結構（`dashboard` / `events`），內部分為 `router`、`service`、`repository`，  
把 HTTP、商業邏輯與 DB 存取分開，方便後續維護與擴充。

## 前端 Dashboard：給不同角色看的同一套事實

前端使用 React + TypeScript + Tailwind CSS，重點不是炫技，而是資訊階層與可讀性：

- **Dashboard 頁面**  
  - 總覽卡片：近期 alert 數量、依 level / type 分布  
  - 時間序列圖：異常事件隨時間的變化  
  - 服務彙總：哪個服務近期最常出事  

- **Events 列表頁**  
  - 可依 alert_type / alert_level / user_id 過濾  
  - 支援分頁與排序  
  - 一眼看到關鍵訊息（時間、來源、標題、等級）  

- **Event 詳細頁**  
  - 展示完整訊息、tags、metrics  
  - 給 SRE / 工程師快速理解 context  

這個 Dashboard 的定位比較像「真實世界會用的工具」，  
而不是只為了作品集做的靜態展示頁。

## 執行與部署：用 Docker 把複雜度封裝起來

為了讓這個系統容易在本地與 demo 環境跑起來，我用 Docker Compose 管理所有服務：

- `broker`：Kafka（KRaft 模式，無 Zookeeper）  
- `db`：PostgreSQL + healthcheck  
- `api`：FastAPI 應用  
- `frontend`：React 應用，production build 由 nginx 提供  
- 開發用容器：producers / consumers 可以在同一 network 裡直接連 Kafka / DB  

環境變數集中在 `infra/docker/.env`：  
Kafka、Postgres、S3、Discord webhook 等設定都在這裡，  
讓「啟一整套系統」變成幾個固定步驟，而不是一堆散落的指令。

## 結果與學到的事

完成這個專案後，我得到幾個對「資料平台 + 即時管線」很具體的感受：

1. **多平台不是問題，沒有統一事件來源才是問題**  
   Kafka 讓事件可以一次產生、多個下游各自處理；S3 + Postgres 則界定了「原始」與「整理後」的責任邊界。

2. **先把 rule-based 做好，ML 會自然有位置**  
   一套合理的規則系統，可以快速創造價值，也為未來的模型準備好了帶標記的訓練資料。

3. **可觀測性與回溯能力要從 Day 1 設計進來**  
   沒有 S3 備援與統一 `anomaly_events` 表，要 debug 或做事後分析都會非常痛苦。

4. **資料工程不只是「做 ETL」，也是在設計產品的觀測介面**  
   把事件整理成 API + Dashboard，是讓其他團隊（SRE、風控、產品）能真正用到這條管線的關鍵。

5. **好的本地開發體驗，讓你願意長期維護 side project**  
   有 docker-compose、遷移工具、清楚的資料流設計，這個專案在未來要拿來 demo、延伸或重構都很輕鬆。
